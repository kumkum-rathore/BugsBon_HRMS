# Bugsbon HRMS API v1

Base URL: `http://localhost:5000/api/v1`

## Response envelope

Success:
```json
{"success":true,"message":"Request completed successfully.","data":{},"meta":null}
```

Error:
```json
{"success":false,"message":"Please log in.","error":{"code":"AUTHENTICATION_REQUIRED","details":[]}}
```

Authenticated endpoints require `Authorization: Bearer <accessToken>`. Web clients use the `hrms_refresh` HttpOnly cookie for refresh/logout. Mobile clients should send `X-Client-Type: mobile`; login and refresh return a refresh token in the response body for storage in iOS Keychain / Android Keystore. Do not store mobile refresh tokens in plain text storage.

## Auth

### `POST /auth/login`
Body: `{ "email": "admin@example.com", "password": "..." }`

Returns safe user fields and a short-lived access token. In browser mode, refresh token is set as an HttpOnly cookie. In mobile mode (`X-Client-Type: mobile`), the refresh token is returned in the response body.

### `POST /auth/refresh`
Web: send request with cookies enabled. Mobile: `{ "refreshToken": "..." }` and `X-Client-Type: mobile`. Refresh tokens rotate; clients must replace the old token with the returned token.

### `POST /auth/logout`
Web: send cookies enabled. Mobile: `{ "refreshToken": "..." }` with `X-Client-Type: mobile`.

### `GET /auth/me`
Bearer access token required. Returns current active account.

## Dashboard

### `GET /dashboard/summary`
Returns employee, branch, attendance and pending-leave counts scoped to the caller's branch unless caller is Super Admin.

## Branches

### `GET /branches?page=1&limit=20&search=&status=ACTIVE`
Super Admin can list all branches. Branch Admin can only list their own branch.

### `POST /branches`
Super Admin only. Example body:
```json
{
  "branchCode":"IND-01",
  "name":"Indore Office",
  "address":{"line1":"Office address","city":"Indore","state":"Madhya Pradesh","country":"India"},
  "officeLocation":{"type":"Point","coordinates":[75.8577,22.7196]},
  "geofenceRadiusMeters":100,
  "timezone":"Asia/Kolkata"
}
```
GeoJSON coordinate order is `[longitude, latitude]`.

### `PATCH /branches/:id`
Super Admin only. Update branch settings. Branch code is immutable after creation.

## Employees

### `GET /employees?page=1&limit=20&search=&status=ACTIVE`
Super Admin sees all; branch-scoped managers are filtered to their own branch.

### `POST /employees`
Branch Admin only. A shift created for the same branch is required. A new employee can optionally be assigned a job-title role; permissions are assigned to the employee independently of that role. Body example:
```json
{"firstName":"Asha","lastName":"Sharma","email":"asha@example.com","password":"Use-a-unique-password-123!","role":"EMPLOYEE","customRoleId":"<optional job-title role ObjectId>","permissions":["task.submit","attendance.self"],"departmentId":"<optional department ObjectId>","shiftId":"<branch shift ObjectId>","hasPreviousExperience":true,"experienceYears":3,"previousCompanyName":"Example Ltd","previousCompanyLeavingDate":"2026-09-30","previousCompanyLeavingReason":"Career growth"}
```
The employee's `permissions` list is checked against permissions granted to the Branch Admin and stored on the employee account. Role records are job-title labels only and do not contain permissions. Employee codes are generated by the API using the branch code and a branch-scoped sequence (for example, `IND-01-EMP-00001`); do not send `employeeCode`. The selected shift is stored on the new employee account and used by attendance and payroll. If `hasPreviousExperience` is true, `experienceYears`, `previousCompanyName`, `previousCompanyLeavingDate` and `previousCompanyLeavingReason` are required; otherwise experience is stored as zero and previous-company details are cleared. Initial password is set by the manager; a real deployment should add invitation/password-change flows before onboarding real employees.

### `PATCH /employees/:id`, `DELETE /employees/:id`, and `DELETE /employees/:id/archive`
Users with `employee.update` can update an employee's status and details. Setting `status` to `ACTIVE` clears the leaving date; setting it to `INACTIVE` or `SUSPENDED` invalidates existing sessions and removes the employee from project memberships. `DELETE /employees/:id` remains a reversible soft deactivation. Use `DELETE /employees/:id/archive` to hide an employee from the directory; the employee and HR history remain stored. Inactive and archived accounts cannot authenticate or be assigned to tasks or projects. Reactivated employees regain account access but must be explicitly added to projects again.

## Attendance

### `GET /attendance?date=YYYY-MM-DD&branchId=<id>`
Employee sees own records; branch-scoped roles see their branch; Super Admin may filter by branch.

### `POST /attendance/check-in` and `POST /attendance/check-out`
Body: `{ "latitude": 22.7196, "longitude": 75.8577 }`. The API uses server timestamps, checks distance to the employee's active branch geofence and records the approximate distance. Employees assigned to a shift who check in more than two hours after shift start are marked `HALF_DAY`; check-in is not required on branch holidays. Location spoofing cannot be fully prevented by GPS alone. Employees must be assigned to a branch.

## Leave requests

### `GET /leaves?status=PENDING&branchId=<id>`
Employees see their own requests; managers are branch-scoped; Super Admin may view all.

### `POST /leaves`
Body: `{ "leaveType":"CASUAL", "startDate":"2026-11-02", "endDate":"2026-11-03", "reason":"Personal commitment" }`.

### `PATCH /leaves/:id/decision`
Manager roles only. Body: `{ "status":"APPROVED", "decisionNote":"Optional note" }`. Only pending requests can be decided once.

## Status codes
- `200` success
- `201` created
- `400` validation error
- `401` missing/invalid authentication
- `403` forbidden / outside geofence
- `404` resource or route not found
- `409` duplicate/conflicting state
- `429` rate limit exceeded
- `500` unexpected server error

## Additional HRMS modules

All routes below are prefixed by `/api/v1` and require a valid Bearer access token unless noted.

### Departments and roles
- `GET /departments` — list permitted branch departments
- `POST /departments` — `{ "name": "Engineering", "description": "..." }`; the branch-scoped department code is generated automatically.
- `PATCH /departments/:id` and `DELETE /departments/:id` — users with `department.create` can edit and soft-archive departments in their branch. Existing employee references are retained.
- `GET /roles` — list global roles for Superadmin or branch roles for Branch Admin
- `POST /roles` — Branch Admin with `role.create` creates a branch-scoped job-title role using `{ "name": "Recruiter", "description": "..." }`. Roles do not have permissions.
- `PATCH /roles/:id` and `DELETE /roles/:id` — Branch Admin with `role.create` can edit and soft-archive branch roles; existing employee role references are retained.
- The first `GET /roles` by a Branch Admin creates the branch's default `Manager` and `HR` job-title roles. Created roles are selected for employees during employee creation.
- Permissions are selected per employee during employee creation and are checked against permissions granted to the Branch Admin. Navigation and API actions use the employee's own permission list.
- `employee.salary.manage` grants branch-scoped salary record management.

Permission catalogue includes `branch.view`, `employee.view`, `employee.create`, `employee.update`, `employee.salary.view`, `employee.salary.manage`, `task.view`, `task.assign`, `task.submit`, `task.review`, `attendance.view`, `attendance.self`, `attendance.manage`, `leave.apply`, `leave.view`, `leave.approve`, `document.upload`, `document.view`, `document.verify`, `calendar.view`, `calendar.manage`, `department.view`, `department.create`, `role.create`, `project.view`, and `project.manage`.

### Tasks and submissions
- `GET /tasks` — employees see only tasks assigned to them
- `GET /tasks/reviewers` — active users available as reviewers in the caller's branch
- `GET /tasks/reviews` — list submitted tasks awaiting review by the signed-in user
- `POST /tasks` — `{ "title": "Test release APK", "description": "...", "assignedTo": "USER_ID", "dueDate": "2026-11-01", "priority": "HIGH", "taskType": "TESTING" }`
- `PATCH /tasks/:id` and `DELETE /tasks/:id` — users with `task.assign` can edit and soft-archive branch tasks. Task editing is locked while a task is submitted for review or approved; submissions, work logs, and activity history are retained.
- When a project is selected, its assignee must be an active employee already selected as a member of that project.
- `PATCH /tasks/:id/progress` — `{ "progress": 40 }`
- `PATCH /tasks/:id/checklist` — `{ "index": 0, "completed": true }`; checklist completion automatically calculates task progress, including 100% when every item is checked.
- `PATCH /tasks/:id/submit` — `{ "submittedTo": "REVIEWER_USER_ID", "note": "Tested build; bugs attached", "files": [{ "name": "bug-report.pdf", "url": "PRIVATE_STORAGE_KEY.pdf", "mimeType": "application/pdf", "size": 12345 }] }`
- `PATCH /tasks/:id/review` — `{ "decision": "CHANGES_REQUESTED", "note": "Crash on login; please fix" }` or `decision: "APPROVED"`.
- `GET /tasks` and `GET /tasks/reviews` include the latest 50 task activity entries with actor and timestamp for authorized task participants and reviewers.

### Calendar and shifts
- `GET /calendar?month=2026-10` — view branch holidays, shifts and the signed-in user's shift
- `POST /calendar/holidays` — Branch Admin adds `{ "date": "2026-10-21", "title": "Holiday name" }`
- `DELETE /calendar/holidays/:id` — Branch Admin removes a branch holiday
- `POST /calendar/shifts` — Branch Admin creates `{ "name": "Morning", "startTime": "09:00", "endTime": "17:00" }`; the grace period is two hours
- `PATCH /calendar/shifts/assign` — Branch Admin assigns or changes an employee's shift with `{ "userId": "EMPLOYEE_ID", "shiftId": "SHIFT_ID" }`; a shift cannot be cleared

### Salary, documents and account
- `GET /salaries` — employees see only their own records; Branch Admins see records for their branch, including attendance deduction breakdowns
- Salary deductions use scheduled weekdays excluding weekends and branch holidays. Approved leave, past unrecorded workdays and half-days are deducted from the monthly net; marking a salary paid stores a payroll snapshot.
- `POST /salaries` — employee/month/base salary/allowances/deductions/bonus
- `PATCH /salaries/:id/status` — `DRAFT`, `PROCESSED` or `PAID`
- `GET /documents` — employees see their own documents; branch admins and authorized reviewers can view branch documents
- `POST /documents` — upload a document for the signed-in employee; branch HR can also upload for employees in their branch
- `PATCH /documents/:id/review` — branch document verification by authorized reviewers
- `POST /uploads` — multipart form field named `file`, maximum 25 MB; returns a private storage key
- `GET /uploads/:key` — authenticated and scope-checked download
- `GET /documents`, `POST /documents`, `PATCH /documents/:id/review`
- `PATCH /employees/:id` — users with `employee.update` update employee status, leaving date, phone, department, experience and delegated permissions
- `DELETE /employees/:id` — users with `employee.update` soft-deactivate an employee while preserving historical records
- `PATCH /account/password` — `{ "currentPassword": "...", "newPassword": "at-least-12-chars" }`

Do not store publicly accessible file URLs. Uploads are served through the authenticated endpoint, and file metadata must be associated with a document or task submission to grant access.


## Corrected branch and role permission workflow
- `GET /api/v1/branches`: Superadmin sees all branches; Branch Admin receives only their assigned branch.
- `POST /api/v1/branches`: Superadmin only. Creates the branch and its Branch Admin account with the initial password.
- `GET /api/v1/employees`: Superadmin can view basic employee directory data across branches (salary amount is omitted); Branch Admin is restricted to their branch; employee access is controlled by permissions on each employee account.
- `POST /api/v1/employees`: Branch Admin only. The `customRoleId` must refer to a role created within that same branch by its Branch Admin. `departmentId`, when provided, must also belong to that branch.
- `POST /api/v1/departments`: Branch Admin only and always scoped to their own branch.
- `POST /api/v1/roles`: Branch Admin only. Creates a branch-scoped custom role with no permissions by default.
- `GET /api/v1/roles`: Branch Admin sees only their branch's roles; Superadmin sees branch-created roles across branches.
- Employee permissions are assigned per employee during creation and are not inherited from or configured on a role.
- `POST /api/v1/salaries` and `PATCH /api/v1/salaries/:id/adjustment`: Branch Admin only. Salary adjustments require a reason and retain previous/updated values in `adjustmentHistory`.
